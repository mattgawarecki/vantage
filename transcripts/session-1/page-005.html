The biggest gap: the spec optimizes for the wrong "interesting"

Vantage — Design Review Findings (prioritized)

Blockers

1. No eval/feedback loop for the headline feature ("interesting"). The entire product pivots on "surface interesting code," yet scoring is a hand-weighted sum with hand-tuned anti-signals and zero ground truth. There is no way to know if the feed is good, no precision metric, no labeled set. The testing section only checks that each rule fires, not that the ranking is useful. This is the single biggest gap given the task's "how would we know it's good?" question. → Recommendation: Before tuning weights, hand-label ~15–25 files in one real reference repo as interesting / not. Compute precision@10 of /interesting against it and iterate weights to that number. Even a tiny labeled fixture converts "vibes" into a regression test and gives you a demo talking point ("87% of the top-10 were independently judged interesting").

2. The depth gauge (a whole pillar) degenerates on real React apps. Three compounding problems the spec doesn't resolve: - Disconnected nodes. depth: number has no sentinel. On any real repo, a large fraction of files (tests, stories, scripts, configs, unreferenced/dead code) are unreachable from the app entrypoint → undefined depth. The "elevation map" will show half the tree as blank/∞. - Dynamic edges and BFS. Spec tags dynamic:true but never says whether BFS traverses dynamic imports. React apps route via React.lazy(() =&gt; import()). If dynamic edges aren't traversed, every lazy-loaded route subtree becomes disconnected — i.e. most feature code shows "unknown depth." If they are traversed, say so and test it. - Barrel files collapse depth. An index.ts that re-exports a directory makes everything ~1 hop from any importer, flattening the gauge to depth 1–2 everywhere. → Recommendation: Define an explicit depth: number | null sentinel and a UI state for "unreachable." Traverse dynamic edges in depth BFS (keep dynamic only for styling). Add a barrel-detection/collapse pass (or at least a fixture test proving a barrel-heavy repo still produces a sane gauge). Demo on a repo you've verified produces a non-degenerate elevation map.

Major

3. Entrypoint fallback heuristic is backwards. "Fallback: highest-fan-in roots." Entrypoints have high fan-out and near-zero fan-in (nothing imports main.tsx). Highest-fan-in selects a deep shared util as the "entrypoint," which inverts the entire depth gauge. Also, for a Vite React app package.json#main is usually absent or points at a build artifact — the real chain is index.html → src/main.tsx. → Recommendation: Fallback should be orphan roots (zero internal fan-in, non-trivial fan-out). Make index.html script-tag resolution the primary path for Vite repos, not a tail case.

4. ts-morph full-program parse + double parsing = perf bottleneck and blocking analyze. You parse the repo twice (dependency-cruiser and ts-morph). ts-morph's default Project builds a full type-checker program — slow and memory-heavy on a medium repo (tens of seconds, hundreds of MB). None of the v1 signals need type info; they're syntactic (hook calls, identifiers, import()). /analyze is synchronous and blocking with only a spinner — a 30s+ hang with no ETA is an ugly demo moment. → Recommendation: Run ts-morph without type resolution (skip adding to program / use the lightweight AST path), parse files individually, and cap repo size for v1. Add coarse progress reporting or pick a demo repo small enough to analyze in <5s. Measure on your target repo before committing.

5. unclear-name is a false-positive machine and undercuts the core promise. data, e, i, tmp are idiomatic React/JS — const { data } = useQuery(...), event handlers, map indices. This signal will fire on nearly every file, producing exactly the boilerplate noise the product claims to suppress. "Export name vs file mismatch" also misfires on index files, HOCs, and re-exports. → Recommendation: Cut it from v1, or scope it hard: only exported public API identifiers, whitelist data/e/i/err/ctx/props/ref, ignore locals and callback params. It's the weakest signal and the most likely to embarrass.

6. Scoring normalization is unspecified and unstable on small/degenerate repos. "Weighted sum → 0..1" with no normalization scheme. Min-max is dominated by a single outlier; tiny or single-package repos produce meaningless scores. The complexity gate ("real logic," "branching") is also vaguer and more work than it reads. → Recommendation: Specify the normalization (sigmoid/percentile, not raw min-max) and define the complexity gate concretely (cyclomatic-ish branch count + LOC threshold). Add a degenerate-repo test.

Minor

7. Type-only imports inflate fan-in. import type are not runtime deps but will count as edges/dependents, distorting high-fan-in toward type-definition modules. dependency-cruiser exposes dependency-type; decide whether to drop type-only edges (recommended for fan-in; arguably keep for depth).

8. heavily-tested has a graph tension and questionable value. To count test→module references, test files must be nodes — but tests are excluded from depth and the interesting feed, and you don't want them inflating the graph elsewhere. Also: well-tested code is often the stable, safe code a newcomer needs least. Reconsider whether this earns a slot in a 6-signal v1.

9. mtime-based cache key is fragile. git checkout/clone don't reliably bump mtimes; you may serve stale analysis. Fine for a demo, but prefer content hashing of a file-list digest if cheap, and note the limitation.

10. No parse-failure resilience stated. One file with unsupported syntax (decorators, newer TS, JSX edge cases) must not crash /analyze. Specify skip-and-report behavior; add a malformed-file fixture.

11. Scroll-sync (Monaco ↔ annotations) is underestimated UI work. Bidirectional line-anchored sync is genuinely finicky and easy to lose a day on. Budget for it or make it one-directional (glyph click → scroll panel) in v1.

Monorepo-as-target and multi-tsconfig. dependency-cruiser keys off one tsconfig for path resolution; a target repo with project references / multiple tsconfigs will mis-resolve aliases and spuriously produce orphans. State that v1 assumes a single-tsconfig repo, and choose your demo repo accordingly.

13. LLM cost/latency is fine architecturally (explain cached, key-optional degradation is the right call). Minor: /ask pulling dependents source slices can blow the token budget for a popular file even after score-truncation — cap dependent count explicitly, not just by score. Verify model IDs against current Anthropic docs as the spec already plans.

Sound enough to start building — but only after three corrections, two of which are cheap. The architecture (isolated analyzer → thin Fastify cache → React Query/Monaco front end, key-optional LLM, form-factor deferral) is well-reasoned and the workspace split is right. However, the design currently has no way to prove its headline claim is good (finding 1), and the depth pillar will visibly degenerate on exactly the React apps it targets (finding 2: disconnected nodes, untraversed dynamic edges, barrel collapse) unless those cases are handled up front. 6	## Brand / metaphor
7	
8	**Project name: Vantage.** The product is framed as **orienteering** through a
9	codebase — exploring unfamiliar code is pathfinding on a hike. The metaphor drives
10	naming and UI language:
11	
12	- **Orienteering** — the overall goal: find your bearings in unknown terrain.
13	- **Elevation map** — the depth gauge. Depth from the entrypoint reads as
14	  elevation/terrain.
15	- **Trail markers** — the interesting-code annotations. Signals are markers along
16	  the trail worth stopping at.
17	
18	Use this vocabulary in UI copy and component names where it reads naturally
19	(e.g. "elevation" for the depth tab, "trail markers" for annotations). Technical
20	identifiers in code/data model stay literal (`depth`, `Signal`) for clarity.
21	
22	## Purpose
23	
24	A web application that helps new engineers orient themselves in an existing
25	**TypeScript + React** codebase. It is a navigation and familiarity tool — not a
26	linter or bug finder. Two core strengths:
27	
28	1. **Surface "interesting" code** — automatically point out the code worth a new
29	   engineer's attention, while suppressing boilerplate noise.
30	2. **Orient relative to a reference point** — show how deep the current code sits
31	   relative to a reference (usually an entrypoint) via a "depth gauge," plus its
32	   dependency neighborhood.
33	
34	Scope is restricted to TypeScript/React repositories. v1 reads a **local repo
35	path**; remote git URLs are a possible later extension.
36	
37	## Definition of "interesting"
38	
39	Interesting = signal-dense, unusual, or structurally important code. Explicitly
40	**not** interesting: boilerplate — plain array iteration (`.map`/`.filter`),
41	simple presentational component trees, pure prop-drilling, trivial conditionals,
42	and trivial-but-popular utilities.
43	
44	Signals are computed by static analysis, then optionally explained in prose by
45	Claude on demand.
46	
47	### v1 signal set
48	
49	| kind | static rule (v1) |
50	|---|---|
51	| `high-fan-in` | many **repo-internal** dependents **AND** clears a min-complexity bar (see edge cases) |
52	| `complex-state` | density of `useState` / `useReducer` / `useContext` / `useEffect`; flag dense clusters |
53	| `unclear-name` | single-char / abbreviated / generic identifiers (`data`, `tmp`, `foo`); export name vs file mismatch |
54	| `boundary-crossing` | implicit client↔server crossings — `fetch` / `axios` / `'use server'` / route handlers |
55	| `heavily-tested` | count of test files (`__tests__`, `*.test.*`, `*.spec.*`) referencing the module |
56	| `dynamic-import` | `import()`, `await import()`, `React.lazy(() => import())` — flagged via dependency-cruiser `dynamic:true` + ts-morph line anchor |
57	
58	Deferred signals (post-v1): `heavily-documented` (comment-line ratio), `anomaly`
59	(breaks local convention, e.g. lone default-export among named, deep relative
60	`../../..` imports), symbol-level granularity.
61	
62	### Scoring
63	
64	Each file gets `score` (0..1) = weighted sum of signals **minus** boilerplate
65	anti-signals. `score` ranks the "interesting feed"; per-file `signals[]` drive
66	the line-anchored annotations.
67	
68	### Edge cases for "highly used" code
69	
70	- **Trivial popular utils are not interesting.** `high-fan-in` fires only when
71	  internal fan-in is high **and** the file clears a min-complexity gate
72	  (LOC / branching / real logic). A one-line `cn()` or `formatDate` used
73	  everywhere is infrastructure noise → suppressed, or demoted to a quiet
74	  "common util" tag rather than an interesting annotation.
75	  `score(high-fan-in) = f(internal_fanin) × complexity_gate`.
76	- **External packages never count.** dependency-cruiser excludes `node_modules`
77	  (`doNotFollow` + exclude). Fan-in counts only repo-internal dependents; imports
78	  of `react`, `lodash`, etc. are not nodes and do not inflate centrality. The
79	  graph is first-party code only.

interface Props {

interface TreeDir {
  name: string
  dirs: Map<string, TreeDir>
  files: FileNode[]
}

function buildTree(nodes: FileNode[]): TreeDir {
  const root: TreeDir = { name: '', dirs: new Map(), files: [] }
  for (const node of nodes) {
    const parts = node.id.split('/')
    const file = parts.pop()!
    let dir = root
    for (const part of parts) {
      if (!dir.dirs.has(part)) {
        dir.dirs.set(part, { name: part, dirs: new Map(), files: [] })
      }
      dir = dir.dirs.get(part)!
    }
    dir.files.push(node)
  }
  return root
}

        return (

      }
    })
